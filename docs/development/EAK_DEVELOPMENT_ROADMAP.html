KiCad editing experience + Herdr-style agent workspace

Design by hand.
Design with your coding agent.
Keep one engineering project.

V1 product requirement: EAK combines KiCad's real schematic, PCB, and 3D experience with persistent terminals. Users run their preferred coding agent in a terminal and ask it to add, edit, move, rotate, place, and route design objects through EAK. Users can also edit manually and access all import/export options available in the selected KiCad build.

Electronics workspace

Actual KiCad editing tools, selection, properties, libraries, connectivity, interactive routing, undo/redo, and 3D inspection—not a read-only SVG approximation.

AI & terminals workspace

Real PTYs, tabs, splits, resize, detach/reconnect, and user-installed coding agents. No mandatory model, provider, or EAK-hosted chat service.

Shared design & outputs

Manual and agent operations address the same objects and revision. Inspect changes, retain recovery points, run checks, and export through KiCad's native capabilities.

Example journey: Open a project → start a coding agent → “Add this connector and wire its power pins” → inspect the proposed change → apply → “Move J1 to the left edge and rotate it 90°” → manually refine placement → ask for a route → inspect DRC and 3D → export the fabrication package.

This roadmap updates the V1 implementation priority. It does not claim those capabilities already exist, replace every older architecture document, or authorize a product-code rewrite. Preserve useful EAK validation, provenance, units, and history while making real editing the first deliverable. Reconcile older provider-first and projection-only specifications during Phase 00.

Herdr-compatible terminal service owns processes and sessions.
EAK owns accepted engineering revisions, provenance and operation history.
KiCad owns the live editable document representation inside each editor.
Reconciliation connects these responsibilities; two independent writers do not.

1. Prove native UI integration before committing to the shell

The final target is the actual editable KiCad experience inside the EAK workspace. Start with a coordinated EAK + native KiCad process prototype to prove commands and synchronization. This is an intermediate integration demonstration, not completion of the in-workspace UI requirement.

For the integrated product, evaluate a thin KiCad-derived native host/dock with a terminal frontend, retaining the Rust EAK service out of process. Compare it with a proven supported native-host approach before retaining Tauri as the main shell. Do not promise that reparenting a wxWidgets window into a webview works across Windows, Linux/Wayland and macOS. Keep the native-host patch small; do not reimplement all three editors in React.

Phase 01 must demonstrate: editing, focus/shortcuts, menus/dialogs, clipboard, DPI, accessibility, undo, 3D acceleration and lifecycle on each claimed platform. If only companion windows work, label that build a preview and record the remaining integration work.

2. Keep terminal transport separate from engineering commands

Prefer a version-pinned Herdr process adapter using its public CLI/API over copying its runtime into EAK. Prove a real terminal presentation path separately: the socket control API is not automatically a lossless PTY byte-stream API. Use a supported attach/client path or explicitly implement and test the needed client adapter. Do not scrape screen text to reconstruct the circuit.

Expose a discoverable EAK CLI with structured JSON inputs/results, plus optional MCP wrappers for agents that support them. A terminal can host arbitrary commands; automatic agent detection/resume and EAK tool use require a tested compatibility path. No promise that every agent supports every optional integration.

3. Coordinate manual and agent changes without data loss

  • Resolve project/document IDs and stable KiCad object UUIDs; include sheet-instance paths, units, angles, layer and coordinate frame. Repeated sheet instances and duplicate reference labels must not target the wrong object.
  • Every agent request carries a request ID and expected revision; reject stale edits, show a semantic preview and group the accepted edit for undo. Destructive changes require explicit approval.
  • Use KiCad's staged edit APIs where supported; inspect per-item results even if the overall request succeeds. Read back the applied state before reporting success. Do not assume a batch is atomic without testing partial failures and cancellation.
  • Track manual edits and undo/redo through supported notifications or authoritative reconciliation reads. Unsaved editor changes must be included; file watching alone cannot see them. Pause agent writes when synchronization is uncertain.
  • Retain complete native documents and assets as revision artifacts. EAK's partial model must never rewrite away unknown KiCad fields. Imported or manually edited states can be recorded with findings; accepted history does not mean manufacturing approval.
  • Journal cross-process operations and recover interrupted edits; never claim an atomic transaction across KiCad and EAK merely because both have local undo/history.
  • Constrain EAK tools to the selected project, validate paths and arguments, and keep credentials out of logs. A coding agent with unrestricted shell access is not sandboxed by these tools; direct file edits are external changes to reconcile, not trusted EAK operations.

4. Respect the real upstream boundaries

  • KiCad: most source is GPL-3.0-or-later. Reusing/linking its editors in a combined distributed application requires a GPL-compatible distribution and corresponding-source/notices review; do not label copied KiCad code MIT/Apache. Process separation is an architectural option, not a blanket legal exemption.
  • Herdr: Apache-2.0 at the inspected revision; retain its license/notices and review vendored dependencies if redistributed. No Herdr source is copied by this roadmap.
  • Libraries: inspect the exact symbol/footprint/model licenses and exceptions before bundling. Code licensing does not automatically cover datasheets, models or third-party component data.
  • Version contract: freeze tested KiCad/Herdr releases or explicitly identified development builds. Capability probes must distinguish unavailable, unsupported, untested and failed operations.
  • Routing: adding track objects is not equivalent to invoking KiCad's interactive router or a full autorouter. RunAction explicitly warns that internal action names are not stable APIs; do not base production routing on undocumented action strings.
  • Persistence: Herdr detach can preserve running processes while the server lives. A server/machine restart restores layout and may resume supported agent sessions; it does not preserve arbitrary running processes.

Dependency-ordered implementation plan

All phases below are planned / not acceptance-tested. Existing code can satisfy individual checks after validation; no percentage is inferred from file counts or old reports.

00 · Establish a truthful build baseline Planned

Dependency: none. Focus: current EAK, not an assumed rewrite.

  • Reproduce Rust, frontend and desktop builds; restore real compilation/tests in CI and retain failure evidence.
  • Pin candidate KiCad and Herdr versions, inventory installed capabilities, and reconcile older specs with this terminal-agent V1 direction.
  • Separate fixture/demo modes from real design operations; remove stale progress claims and document existing components that can be reused.

Exit: another developer reproduces the baseline; every claimed passing check actually executes and failures are recorded rather than disabled.

01 · Prove the actual KiCad UI hosting strategy Planned

Dependency: 00. Highest-risk integration proof; do this before a UI rebuild.

  • Launch real schematic, PCB and 3D tools on one project; demonstrate an API-driven edit and a manual edit.
  • Prototype a thin native host/dock and terminal presentation. Compare against companion-process integration; document the chosen boundary, lifecycle and platform limitations.
  • Verify licensing/distribution obligations before incorporating upstream code. Test focus, shortcuts, dialogs, clipboard, DPI, graphics and undo on the platforms claimed.

Exit: a demonstrated route to actual editable KiCad surfaces inside EAK. Separate windows prove only the intermediate preview, not final integrated-UI acceptance.

02 · Shared project state and lossless reconciliation Planned

Dependencies: 00, 01.

  • Implement create/open/save/reopen and capture full native documents, assets, accepted revisions, stable IDs and EAK provenance.
  • Coordinate unsaved manual changes, agent proposals, revision checks, single-writer ownership, undo/redo and semantic diffs.
  • Handle partial failures, interrupted commits, reconnects and unknown native objects without overwrites or lossy reserialization.

Exit: manual edit → agent reads current revision → agent edit → manual undo → save/reopen preserves the expected objects, connectivity and history.

03 · Herdr-style persistent terminal workspace Planned

Dependencies: 00, 01; can proceed alongside 02 once interface boundaries are fixed.

  • Integrate a named, project-scoped Herdr session through its supported public surface; keep server-owned terminal identity separate from EAK panel layout.
  • Provide real interactive terminals with keyboard input, ANSI/full-screen applications, resize, clipboard, tabs, splits, focus and attach/detach.
  • Bootstrap/reconcile state on reconnect; test output backpressure, agent status and optional native session resume. Do not promise process survival after server restart.

Exit: three concurrent terminals, including two different coding agents and a shell, remain usable after UI detach/reconnect without losing live processes while the server stays running.

04 · Agent-neutral EAK tools Planned

Dependencies: 02, 03.

  • Provide discoverable CLI/JSON tools for project context, selection, object queries, proposing/applying edits, checks and export jobs; add optional MCP without making it mandatory.
  • Use structured IDs, units, angles, request IDs, revision preconditions, permissions, previews and per-item errors. Allow user-selected agents/models; no mandatory NIM or embedded LLM.
  • Supply tool-use instructions and verify compatibility with at least two independent coding agents. Run arbitrary unsupported terminal programs without pretending detection or tool integration is guaranteed.

Exit: both agents inspect the same project and execute an approved reversible edit through EAK tools, with read-back evidence and an audit trail.

05 · Real schematic editing, manual and agent-driven Planned

Dependencies: 01, 02, 04.

  • Expose native symbol/library placement, properties, movement, orientation, wires, labels, junctions and hierarchical sheets.
  • Implement validated agent operations for the same objects, preserving real pin numbers, symbol/footprint assignments and sheet-instance identity.
  • Verify schematic API coverage for the pinned build. If required editing operations are missing, record and implement a bounded native adapter; do not silently fall back to unsafe text replacement.

Exit: agent adds/wires/rotates a real component, user edits it manually, and KiCad ERC/netlist plus reopen confirm intended connectivity and undo behavior.

06 · PCB component placement and orientation Planned

Dependencies: 05.

  • Transfer schematic changes through KiCad's supported update path while preserving symbol-to-footprint identities and nets.
  • Enable manual and agent add/move/rotate/flip/property operations, board-edge references, placement constraints and locked-item handling.
  • Preserve real pad geometry, placement coordinates, board side, courtyard and 3D model transforms; preview proposed positions before applying.

Exit: “move J1 to the left edge and rotate 90°” changes the intended footprint, retains connectivity, appears in the actual PCB UI and can be manually adjusted/undone.

07 · Guided routing with actual geometry Planned

Dependencies: 06.

  • Retain KiCad's native manual interactive routing, layer/via control, zone refill and applicable differential-pair/length tools.
  • Support bounded agent route proposals using actual pads, nets, tracks, vias, widths, clearances and layers; inspect and validate resulting geometry.
  • Prove any router automation API separately. Where absent, plan a versioned adapter or explicitly labelled user-assisted step; generic item creation or internal RunAction strings do not prove routing integration.

Exit: user guides an agent to route a specified connection; actual endpoints, clearance and DRC are checked, manual adjustment works, and rejected changes remain recoverable. General autonomous autorouting is not implied.

08 · Interactive 3D inspection of the same board Planned

Dependencies: 06; final revision-consistency test also covers 07.

  • Integrate KiCad's actual 3D viewer with board shape, stackup, holes and real component models.
  • Support normal orbit/pan/zoom, visibility and native viewing controls; surface missing models instead of inventing geometry.
  • Refresh the view after manual or agent placement/routing changes and expose render/3D exports separately.

Exit: a known footprint move/rotation and board change appear correctly in PCB and interactive 3D for the same revision, with correct side and model orientation.

09 · Full selected-version import/export catalogue Planned

Dependencies: 05–08; inventory can start after 00.

  • Complete the parity matrix from actual native menus, CLI help and plugins, including operation direction and every exposed option.
  • Connect supported APIs/CLI jobs; make native-only dialogs reachable and labelled. Preserve option defaults, units, origins, file paths, diagnostics and cancellation.
  • Add fixtures for each supported route/format and test material option combinations. Validate output contents and reopen/round-trip where meaningful; record format losses honestly.

Exit: every applicable option in the pinned KiCad distribution is reachable through EAK, its automation level is explicit, and output evidence is tied to a revision. No “all formats” claim from a partial subset.

10 · Verification, recovery and user control Planned

Dependencies: 02, 04–09.

  • Run real KiCad ERC/DRC plus applicable EAK checks; distinguish passed, failed, not run and unsupported. No findings is not proof when inputs/checks are missing.
  • Test stale requests, simultaneous manual/agent edits, partial item failures, cancellation, disconnects, crashes and replay/reopen; never overwrite a newer manual change.
  • Keep previews, approvals, recovery points and export revision checks visible. Manufacturing approval remains explicit and is not a guarantee of physical safety.

Exit: injected failures preserve recoverable documents, bad changes show actionable findings, and repair/recheck never reports a stale or untested revision as verified.

11 · Reproducible installation and license compliance Planned

Dependencies: 01 integration/license decision, 03, 09, 10.

  • Package or document exact native dependencies and model/library paths; detect missing tools and incompatible versions with actionable messages.
  • Supply root README, license texts, third-party notices, corresponding source where required, supported-agent/platform matrix and honest limitations.
  • Test clean installation on each advertised OS. One-OS preview is acceptable when labelled; cross-platform support requires independent evidence, including terminal and native graphics behavior.

Exit: clean-machine install, project open, terminal launch, native editing, 3D and export all work on each claimed platform without developer-local paths.

12 · V1 acceptance: manual + agent + output Planned

Dependencies: all previous acceptance evidence.

  • Execute the complete acceptance scenario on a real example with actual library parts and correct pin mappings.
  • Repeat with two different user-selected coding agents; prove the project also remains manually editable without an AI provider.
  • Publish reproducible commands, expected outputs, limitations and evidence; no fixture-only demonstration may satisfy live product acceptance.

Exit: install → native edit → agent edit → manual refinement → route → ERC/DRC → interactive 3D → import/export → reopen, with one consistent design history.

Concrete V1 acceptance scenario

  1. Install on a supported clean machine and create/open a native KiCad project from EAK.
  2. Open the actual schematic, PCB and 3D surfaces in the EAK workspace. Keep manual editing available without a model account.
  3. Start two different coding agents in persistent terminals; both discover EAK tools and inspect the same project and selected objects.
  4. Ask one agent to add a component with a real library symbol, correct pins and footprint, wire specified connections, edit a property and rotate it. Preview, approve and inspect the change.
  5. Make a manual schematic edit. The other agent reads the updated state, not a stale file or terminal transcript.
  6. Update the PCB, ask for specific placement/orientation, manually refine it, and verify that symbol/footprint/net identities remain consistent.
  7. Guide a bounded routing operation; inspect actual pads, tracks, vias and layer changes. Run ERC/DRC and repair deliberate violations rather than disabling checks.
  8. Inspect the same board in 3D with correct model transforms. Confirm the latest revision is visible.
  9. Exercise the selected-version import/export catalogue, including a manufacturing package. Inspect contents and revision identity; a file's existence alone is insufficient.
  10. Undo/redo, save, close, reopen, and reconnect terminals. Test a stale agent proposal and an interrupted operation without losing manual work.

48-hour milestone: credible preview, not a false V1 claim

The complete integrated product above is the target. The original 48-hour release window should be treated as a conditional developer-preview timebox, not a commitment to finish native UI hosting and full KiCad parity in two days.

  • First: reproduce EAK builds, make CI meaningful, pin the toolchain and document the native integration/license constraints.
  • Then: prove one real manual/agent edit round-trip with a terminal agent, a native KiCad editor and authoritative read-back. If only a companion-window prototype works, say so.
  • Before publication: provide installation steps, licenses, a real example, exact limitations and a clearly labelled preview release. Do not claim full routing, all import/export automation or embedded KiCad UI before those tests exist.
  • If the integration proof fails: publish findings and a source preview rather than manufacturing a success demo. Preserve the full V1 backlog above.
