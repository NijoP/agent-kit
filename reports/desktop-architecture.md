### Tauri Configuration

The Tauri configuration is generated by `npm create tauri-app` / `cargo tauri init`. Key files:
- `app/src-tauri/tauri.conf.json` - Main Tauri config
- `app/src-tauri/build.rs` - Build script for Tauri

### Current IPC Pattern

The Tauri shell uses `tauri::invoke` for frontend→backend calls:

```typescript
// Frontend (TypeScript)
import { invoke } from '@tauri-apps/api/core';

const result = await invoke('run_workflow', { 
    intent: "Design a USB-C PD controller",
    seed: 12345 
});
```

```rust
// Backend (Rust)
#[tauri::command]
async fn run_workflow(intent: String, seed: u64) -> Result<RunReport, String> {
    let cfg = RunConfig { intent, seed, ... };
    eak_cli::run(&cfg).map_err(|e| e.to_string())
}
```

### Areas Needing Attention

| Area | Issue | Priority |
|------|-------|----------|
| **IPC surface** | No formal API schema; commands are ad-hoc | High |
| **Event streaming** | SSE implementation exists but not integrated with kernel event log | Medium |

| **State persistence** | Zustand store not persisted to disk | Medium |

| **Plugin system** | Not designed; no extension points | Medium |
| **Accessibility** | Canvas-based editors have no a11y support | High |

## Critical Architecture Decisions

### 1. Kernel Authority (NON-NEGOTIABLE)
```
The Rust kernel (eak-runtime + eak-engines + eak-phases) is the SOLE authority for:
- Engineering state
- Verification results
- Deterministic replay
- Component/library data

The GUI is a PROJECTION of kernel state, never the source of truth.
```

### 2. Agent/Kernel Boundary
```
┌─────────────────────────────────────────────────────────┐
│                    Agent (LLM)                           │
│  - Proposes: requirements, parts, topology, fixes       │
│  - Queries: library, state, verification results        │
└──────────────────────┬──────────────────────────────────┘
                       │ propose / query (structured)
                       ▼
┌─────────────────────────────────────────────────────────┐
│              EAK Runtime (Kernel)                        │
│  - Validates: every proposal against kernel rules       │
│  - Commits: only validated changes to event log         │
│  - Verifies: runs deterministic verification kernel     │
│  - Emits: events for GUI projection                     │
└─────────────────────────────────────────────────────────┘
                       │ events (committed)
                       ▼
┌─────────────────────────────────────────────────────────┐
│                    GUI (React)                           │
│  - Subscribes: to kernel event stream                   │
│  - Renders: schematic, PCB, panels                      │
│  - Captures: user intent → sends to Agent               │
└─────────────────────────────────────────────────────────┘
```

### 3. Application vs Library Separation

**EAK Application** (installed per-user):
- GUI (Tauri + React)
- Rust runtime (kernel)
- Verification kernel
- Compiler (IR generators)
- Agent orchestration
- Schematic/PCB engines
- **Library Engine** (queries local + remote libraries)

**EAK Component Library** (independently manageable):
- Base library (curated, ships with app)
- Optional library packs (vendor-specific)
- User libraries (private, per-project)
- Remote library index (optional sync)

```
Installer (~200MB)                    Library Storage (~2GB+)
┌─────────────────────────┐           ┌─────────────────────────┐
│ EAK App (~200MB)        │           │ Library Index (~50MB)   │
│ - GUI + Kernel          │           │ Datasheets (~2GB)       │
│ - Compiler + Kernel     │           │ 3D Models (~500MB)      │
│ - Agents + Engines      │           │ Symbols/Footprints      │
│ - Base Library Index    │──────────►│ User Libraries          │
│   (metadata only)       │   sync    │ Vendor Packs (optional) │
└─────────────────────────┘           └─────────────────────────┘
```

## Recommended Architecture Changes

### 1. Formalize IPC Schema
```json
// schemas/ipc.json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "commands": {
    "run_workflow": {
      "input": { "intent": "string", "seed": "u64", "config": {} },
      "output": { "outcomes": [], "state": {}, "log_path": "string" }
    },
    "query_library": {
      "input": { "query": "string", "filters": {} },
      "output": { "parts": [], "assets": [] }
    },
    "get_state": {
      "input": { "entity_ids": [] },
      "output": { "entities": {} }
    }
  },
  "events": {
    "phase_started": { "phase": "string", "timestamp": "u64" },
    "entity_committed": { "entity_type": "string", "entity_id": "u64" },
    "verification_finding": { "rule": "string", "severity": "string", "subjects": [] }
  }
}
```

### 2. Canvas Abstraction Layer
```typescript
// ui/src/canvas/CanvasEngine.ts
interface CanvasEngine {
  render(schematic: SchematicIR): void;
  render(pcb: PcbIR): void;
  onSelectionChange(callback: (ids: EntityId[]) => void): void;
  onViewportChange(callback: (vp: Viewport) => void): void;
  exportImage(format: 'png' | 'svg'): Blob;
}
```

### 3. Kernel Event Stream for GUI
```rust
// In eak-runtime
pub struct GuiEventSink {
    tx: mpsc::Sender<GuiEvent>,
}

pub enum GuiEvent {
    EntityCommitted { entity_type: String, entity_id: EntityId },
    PhaseStarted { phase: String, timestamp: u64 },
    VerificationFinding { rule: String, severity: Severity, subjects: Vec<EntityId> },
    AgentProposal { proposal: Proposal },
    PhaseCompleted { phase: String, outcome: PhaseOutcome },
}

// Runtime exposes:
pub fn subscribe_gui_events(&self) -> mpsc::Receiver<GuiEvent>;
```

## Migration Path for Existing Code

### Phase 1: IPC Schema (Week 1)
- Define JSON schemas for all `invoke` commands
- Generate TypeScript types from schema
- Add runtime validation in Rust

### Phase 2: Kernel Event Stream (Week 2)
- Implement `GuiEventSink` in runtime
- Connect to existing event log
- Frontend subscribes via Tauri event system

### Phase 3: Canvas Abstraction (Week 3-4)
- Extract canvas logic from `PcbCanvas.tsx` / `SchematicView.tsx`
- Create `CanvasEngine` abstraction
- Support both Schematic and PCB modes

### Phase 4: Persistence & Polish (Week 5)
- Add Zustand persistence
- Implement window state restoration
- Add keyboard shortcuts system

## Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Tauri v2 breaking changes | Low | High | Pin Tauri version; test on each update |
| WebView2/WebKit differences | Medium | High | Test on all target platforms (Win/Mac/Linux) |
| Canvas performance at scale | Medium | High | Implement viewport culling, LOD |
| Agent reasoning latency | High | Medium | Streaming responses; async IPC |
| Binary size (Tauri + kernel) | Low | Medium | Strip symbols; optimize deps |

## Conclusion

The current desktop architecture is **fundamentally sound** but needs:
1. **Formalized IPC contracts** (schema-driven)
2. **Kernel event streaming** to GUI (replace polling)
3. **Canvas abstraction** for maintainability
4. **Persistent workspace state** (Zustand + localStorage)
5. **Clear agent/kernel boundary enforcement** (no direct DB access from GUI)

The Tauri + React + Rust kernel architecture is the right choice. The main work is formalizing the contracts between layers and ensuring the kernel remains the sole authority.
